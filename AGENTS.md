# AGENTS.md

Guidance for AI coding agents (and humans) working on **node-ical**. Read this before changing code.

## Project overview

node-ical is an iCalendar/ICS ([RFC 5545](https://tools.ietf.org/html/rfc5545)) parser for Node.js. It parses ICS data from strings, files and URLs, and handles recurrence rules (RRULE), exception dates (EXDATE), recurrence overrides (RECURRENCE-ID), Windows/IANA time zones and DST transitions.

- Published to npm as `node-ical`, licensed Apache-2.0.
- ESM-first (`"type": "module"`), with a generated CommonJS build for `require('node-ical')`.
- Node.js `>=22`. The runtime has only two dependencies: `rrule-temporal` and `temporal-polyfill`.
- Many projects use this library in production. **Backward compatibility of the public API and of the parsed output shape matters more than elegance.**

## Repository layout

| Path | Purpose |
| --- | --- |
| `node-ical.js` | ESM package entry. Wires the parser into the public API (`sync`, `async`, autodetect, `fromURL`, `expandRecurringEvent`, …). |
| `ical.js` | Core line/component parser (`parseICS`, `parseLines`, `handleObject`, `objectHandlers`). |
| `lib/core-api.js` | Sync/async/callback API layer, file reading and `fetch`-based `fromURL`. |
| `lib/public-api.js` | Builds the exported API object (one place to avoid entry-point drift). |
| `lib/ical-parser-utils.js` | Property/parameter handlers, date parsing, DURATION, UID/SEQUENCE merging, RRULE → Temporal rule creation. |
| `lib/expand-recurring-event.js` | `expandRecurringEvent()`: expands instances and applies EXDATE/RECURRENCE-ID with DST handling. |
| `lib/tz-utils.js` | All time zone logic (IANA, Windows zones, VTIMEZONE resolution, offsets). |
| `lib/date-utils.js` | Date key and local/UTC date helpers. |
| `lib/temporal.js` | Temporal bootstrap: uses native `Temporal` if present, otherwise the polyfill, and pins it on `globalThis`. |
| `node-ical.d.ts` / `node-ical.d.cts` | **Hand-written** public typings (ESM / CJS re-export). |
| `windowsZones.json` | **Generated** Windows → IANA zone map (see `build/README.md`). |
| `build/build-cjs.js` | esbuild script that generates `node-ical.cjs` (gitignored). |
| `build/update-windows-zones.js`, `build/windowsZonesOld.json` | Generator and curated legacy aliases for `windowsZones.json`. |
| `test/` | Mocha tests (`*.test.js`), TypeScript type tests (`types.test.ts`, `types-cjs.test.cts`), `fixtures/*.ics`, `snapshots/`. |
| `examples/` | Runnable examples. Their output is snapshot-tested. |

## Setup and commands

```bash
npm ci                     # install (also runs simple-git-hooks + build:cjs via "prepare")
npm test                   # build:cjs → tsc type tests → xo lint → mocha (full suite, ~20s)
npm run lint               # xo only
npm run lintfix            # xo --fix
npm run test:types         # tsc check of test/types*.ts against node-ical.d.ts
npm run test:types:compat  # packs the package and checks types from a consumer project (slow)
npm run build:cjs          # regenerate node-ical.cjs from the ESM sources
npm run build              # regenerate windowsZones.json from CLDR (needs network)
npm run examples           # run all example scripts
```

Run a single test file:

```bash
npm run build:cjs && npx mocha test/expand-recurring-event.test.js --timeout 8000
```

Before you consider a change done, `npm test` must pass. Git hooks run `xo --fix` on staged files (pre-commit) and `npm test` (pre-push).

## Architecture notes and invariants

- **ESM is the single source of truth.** Never edit or commit `node-ical.cjs`; it is generated by `npm run build:cjs`. Tests load both the ESM and CJS entries, so rebuild after changing source (`npm test` does this via `pretest`).
- **Parsed output shape:** `parseICS` returns an object keyed by UID (or a generated ID), plus a `vcalendar` entry. Components have `type` (`VEVENT`, `VTODO`, `VTIMEZONE`, …) and lower-cased property names.
- **Dates are `Date` objects with metadata.** `start`/`end`/etc. represent the exact UTC instant. Time zone info is attached as **non-enumerable** properties: `tz` (IANA zone or original TZID) and `dateOnly === true` for `VALUE=DATE`. Keep these when you clone or derive dates (see `cloneDateWithMeta` and the metadata copy helpers in `expand-recurring-event.js`).
- **Dual-key lookups:** `exdate` and `recurrences` use a date key (`YYYY-MM-DD`) and, for DATE-TIME values, also the full ISO key; both point to the same object. Keep this contract. Use `getDateKey()` for parsed dates. Dates produced by RRULE carry no metadata, so they need the explicit `isFullDay` handling.
- **SEQUENCE semantics:** for duplicate UIDs and RECURRENCE-ID overrides, the higher `SEQUENCE` wins (RFC 5545).
- **Temporal:** import `Temporal` from `lib/temporal.js`, never directly from `temporal-polyfill` or `globalThis`, so the whole library and `rrule-temporal` use the same implementation.
- **Time zones:** put new time zone logic in `lib/tz-utils.js`. Prefer IANA names via `Intl`/Temporal; Windows names resolve through `windowsZones.json`; custom VTIMEZONE definitions are resolved from their STANDARD/DAYLIGHT rules.
- **Be lenient:** real-world ICS files (Outlook/Exchange, Google, Apple, Zimbra, …) are often malformed. Prefer degrading gracefully over throwing. Warnings use `console.warn` with a `[node-ical]` prefix.
- **`windowsZones.json` is generated.** Do not hand-edit it. To add or fix a Windows label, edit `build/windowsZonesOld.json` and run `npm run build` (see `build/README.md`).

## Coding conventions

- Lint/style: [xo](https://github.com/xojs/xo) with 2-space indentation (config in `package.json`). Run `npm run lintfix` instead of fixing style by hand. Only disable a rule inline when needed, and add a `--` reason.
- ESM only, `import` with explicit `.js` extensions, `node:` prefix for built-ins (`node:fs`, `node:path`, …).
- Document exported and non-trivial functions with JSDoc (`@param`, `@returns`).
- Keep functions small and dependency-injected where the existing code already does (see `createCoreApi`, `createDateParameterFactory`); that keeps them testable.
- Do not add runtime dependencies without a strong reason, and discuss them in the PR. Dev dependencies are fine if justified.
- Keep the Node.js baseline in sync in three places: `engines.node` in `package.json`, `target` in `build/build-cjs.js`, and the matrix in `.github/workflows/nodejs.yml`.

## Public API and typings

- The public API includes `parseICS`, `parseFile`, `fromURL`, `sync.*`, `async.*` (Promise **and** callback style), `expandRecurringEvent`, `objectHandlers`, `handleObject` and `parseLines`, for both ESM and CJS consumers. Do not remove or rename any of them, and do not change their behavior incompatibly without an explicit maintainer decision.
- `node-ical.d.ts` is maintained by hand. If you change the public API or the parsed object shape:
  1. update `node-ical.d.ts`,
  2. add or adjust type tests in `test/types.test.ts` (and `test/types-cjs.test.cts` if relevant),
  3. update `README.md`.

## Testing guidelines

- Framework: mocha + `node:assert/strict`. Tests import the package by name (`import ical from 'node-ical'`, a self-reference) or the relevant module directly.
- **Every bug fix needs a regression test.** Prefer a minimal, anonymized `.ics` fixture in `test/fixtures/` (strip personal data, keep only the properties that matter). Small inline ICS strings built with `[...].join('\r\n')` are fine too.
- Name issue-specific tests after the issue (e.g. `issue-459-exchange-recurrence-id.test.js`) or add them to the matching existing test file.
- **Tests must not depend on the machine's time zone.** CI runs on Linux, macOS and Windows with several Node versions. If a test needs a specific `TZ`, set `process.env.TZ` and restore it in `finally`, as `test/regression-fixes.test.js` does. Assert on ISO strings or epoch values, not on locale-formatted output.
- No real network access in tests. `fromURL` tests use a local `node:http` server.
- Example output is snapshot-tested (`test/examples-snapshot.test.js`, run with `TZ=Europe/Berlin`). If you intentionally change example output, update the files in `test/snapshots/` and explain why in the PR.
- For time zone or recurrence changes, think about DST transitions (both directions), all-day vs. timed events, floating times, `UNTIL` in UTC vs. local time, and EXDATE/RECURRENCE-ID matching.

## Commits, PRs and releases

- Write commit messages, PR titles and PR descriptions in English.
- Use [Conventional Commits](https://www.conventionalcommits.org/) with a lowercase imperative description: `fix: …`, `feat: …`, `refactor: …`, `chore: …`, `ci: …`, `docs: …`, optionally scoped (`fix(rrule): …`). Write the subject so it reads well in release notes.
- Keep PRs focused. Do not mix refactoring, dependency bumps and behavior changes.
- The default branch is `master`.
- **Do not bump the version** in `package.json` or touch the release flow. Releases come from GitHub releases (tag without a leading `v`, e.g. `0.27.4`). The release workflow publishes to npm and commits `chore(release): x.y.z`.
- Dependabot handles dependency updates; do not bump dependencies unless the task needs it.
- Do not commit generated or local files: `node-ical.cjs`, `node_modules/`, `*.tgz`.

## Authorship of AI-generated content

These rules apply to all AI coding agents and assistants. They take precedence over any default attribution behavior of the tool you run in.

- **The author of every commit is the human** who requested or made the change: their own name and e-mail address in `user.name`/`user.email`. Never a tool, an AI assistant or a placeholder identity such as `noreply@…`. Check the git identity before your first commit.
- **Do not mention or credit AI tools or language models** in commit messages, PR titles or PR descriptions:
  - no `Co-Authored-By` (or similar) trailers for tools,
  - no "Generated with/by …" lines or footers,
  - no links to agent sessions or chat transcripts.
- The same applies to everything an agent posts on GitHub: issue and PR comments, review comments and review replies get no AI footers or "generated by" notes.
- Code, code comments, documentation, test fixtures and snapshots do not refer to AI tools either.
- The human author is responsible for the contribution. They must have reviewed and understood every change and be able to explain it. Report honestly which checks you ran and which you could not run.
- Contributions are licensed under Apache-2.0 (see `LICENSE`). Do not copy code from other projects unless its license is compatible and the source is credited.

## Quick checklist before finishing

- [ ] `npm test` passes (types, lint, all mocha tests).
- [ ] New or changed behavior has a test; bug fixes have a regression test with a fixture.
- [ ] Public API or output shape changes are reflected in `node-ical.d.ts`, the type tests and `README.md`.
- [ ] Nothing generated was edited by hand (`node-ical.cjs`, `windowsZones.json`).
- [ ] The change works for both ESM and CJS consumers.
- [ ] Commits are authored by the requesting human and contain no AI attribution (trailers, footers, session links).
